# OpenGL primitives

## Scope

This list uses **OpenGL 4.6 core** as the baseline and groups the API into conceptual primitives rather than reproducing every `gl*` entry point. OpenGL is primarily a stateful rendering/compute control API: applications create objects, bind or name them, change context state, and issue draw/dispatch/transfer commands. The literal graphics meaning of *primitive*—points, lines, triangles, and patches—is listed separately under **geometric primitive topology**.

Primary references: [Khronos OpenGL Registry](https://registry.khronos.org/OpenGL/index_gl.php), [OpenGL 4.6 reference pages](https://registry.khronos.org/OpenGL-Refpages/gl4/html/), [OpenGL object overview](https://wikis.khronos.org/opengl/OpenGL_Object), and [rendering pipeline overview](https://wikis.khronos.org/opengl/Rendering_Pipeline_Overview).

## context

An OpenGL context is the stateful API environment against which most OpenGL commands operate. Context creation itself is handled by a window-system binding or platform layer rather than core OpenGL, but once current, the context owns or shares the state and objects used by rendering commands. Sources: [OpenGL Registry](https://registry.khronos.org/OpenGL/index_gl.php) and [OpenGL context](https://wikis.khronos.org/opengl/OpenGL_Context).

## global context state

A large part of OpenGL consists of current state: enabled capabilities, bindings, viewport/scissor rectangles, blend/depth/stencil/rasterization settings, pixel-store parameters, and many other values. Draw and dispatch commands consume the state that is current when they execute, which is the central difference from more explicit APIs such as Vulkan. Source: [OpenGL 4.6 reference pages](https://registry.khronos.org/OpenGL-Refpages/gl4/html/).

## object names and lifetimes

Most OpenGL resources are represented by integer object names created/generated by the API and deleted explicitly. Binding a name or using direct-state-access commands selects the object whose stored state/resources a command changes. Source: [OpenGL Object](https://wikis.khronos.org/opengl/OpenGL_Object).

## buffer objects

Buffers are linear byte stores used for vertex data, indices, uniforms, shader storage, transform feedback, indirect commands, pixel transfer, atomic counters, and other roles selected by binding/use. They are the basic generic GPU memory resource exposed by OpenGL. Source: [OpenGL Buffer Object](https://wikis.khronos.org/opengl/Buffer_Object).

## texture objects

Textures store formatted one-, two-, or three-dimensional image data, arrays, cube maps, multisample images, and related forms, including mipmap levels. Shaders access them through sampling or image operations, while the API controls allocation, upload, views, parameters, and copies. Source: [OpenGL Texture](https://wikis.khronos.org/opengl/Texture).

## sampler objects

Sampler objects hold sampling parameters independently of texture storage: filters, wrap modes, comparison settings, anisotropy where available, and similar state. Binding a sampler to a texture unit lets multiple textures share sampling state or one texture be sampled in different ways. Source: [OpenGL Sampler Object](https://wikis.khronos.org/opengl/Sampler_Object).

## renderbuffer objects

Renderbuffers are image-storage objects intended primarily as framebuffer attachments rather than general shader-sampled textures. They are useful for color, depth, stencil, and multisample attachment storage when texture access is unnecessary. Source: [OpenGL Renderbuffer Object](https://wikis.khronos.org/opengl/Renderbuffer_Object).

## framebuffer objects

Framebuffer objects define the collection of color, depth, and stencil images to which rendering reads/writes are directed. Attachments can come from textures or renderbuffers; completeness rules determine whether the assembled framebuffer is valid for rendering. Source: [OpenGL Framebuffer Object](https://wikis.khronos.org/opengl/Framebuffer_Object).

## vertex array objects

A vertex array object stores how vertex attributes are sourced from buffers: enabled attributes, formats, binding associations, strides/offsets, divisors, and the element/index buffer binding. A draw command interprets its vertex stream through the current VAO. Source: [OpenGL Vertex Specification](https://wikis.khronos.org/opengl/Vertex_Specification).

## shader objects

A shader object contains source compiled for one stage such as vertex, tessellation control/evaluation, geometry, fragment, or compute. Shader objects are attached to program objects for linking; after linking, the program executable is what rendering/dispatch uses. Source: [OpenGL Shader](https://wikis.khronos.org/opengl/Shader).

## program objects

A program object links one or more shader stages into executable shader code and owns the resulting linked interface plus program-level state. The active program supplies programmable stages for draws or compute dispatches. Source: [OpenGL Shader Compilation](https://wikis.khronos.org/opengl/Shader_Compilation).

## program pipeline objects

Program pipeline objects support separable programs by combining independently linked stage programs into one active executable pipeline. They let stage composition be changed without relinking one monolithic program. Sources: [OpenGL Object](https://wikis.khronos.org/opengl/OpenGL_Object) and [glBindProgramPipeline](https://registry.khronos.org/OpenGL-Refpages/gl4/html/glBindProgramPipeline.xhtml).

## transform feedback objects

Transform feedback captures vertex-processing outputs into buffer objects before rasterization. The object stores transform-feedback buffer bindings and associated capture state so transformed geometry/data can be reused without CPU readback. Source: [OpenGL Transform Feedback](https://wikis.khronos.org/opengl/Transform_Feedback).

## query objects

Queries collect asynchronous information about GPU work, such as occlusion/sample counts, timestamps/time elapsed, transform-feedback results, and primitive statistics where supported. The application begins/ends or timestamps a query and retrieves the result later. Source: [OpenGL Query Object](https://wikis.khronos.org/opengl/Query_Object).

## sync objects

Sync objects represent fences in the GPU command stream and allow the application to test or wait for completion of earlier work. They are the main explicit OpenGL primitive for CPU/GPU or GPU-command synchronization. Source: [OpenGL Sync Object](https://wikis.khronos.org/opengl/Sync_Object).

## vertex specification

Vertex specification tells OpenGL where vertex attributes live and how bytes in buffers become typed attribute values. A draw command then selects vertices/indices, and the vertex shader receives the resulting attribute tuples. Source: [Vertex Specification](https://wikis.khronos.org/opengl/Vertex_Specification).

## geometric primitive topology

In OpenGL’s literal graphics terminology, a primitive mode determines how a vertex stream is assembled. Core modes include `GL_POINTS`, `GL_LINES`, `GL_LINE_STRIP`, `GL_LINE_LOOP`, `GL_LINES_ADJACENCY`, `GL_LINE_STRIP_ADJACENCY`, `GL_TRIANGLES`, `GL_TRIANGLE_STRIP`, `GL_TRIANGLE_FAN`, `GL_TRIANGLES_ADJACENCY`, `GL_TRIANGLE_STRIP_ADJACENCY`, and `GL_PATCHES`; primitive assembly ultimately produces points, lines, or triangles (with patches feeding tessellation). Source: [OpenGL Primitive](https://wikis.khronos.org/opengl/Primitive).

## draw commands

Drawing commands such as the `glDrawArrays*` and `glDrawElements*` families launch the graphics pipeline using the current program/pipeline, vertex specification, framebuffer, and fixed-function state. Array draws generate implicit sequential vertex indices; element draws fetch indices from an element buffer. Source: [OpenGL 4.6 reference index](https://registry.khronos.org/OpenGL-Refpages/gl4/html/).

## instancing and indirect drawing

Instanced draws repeat geometry for multiple instances while exposing an instance index and allowing per-instance attributes. Indirect and multi-draw commands read draw parameters from buffers, allowing the GPU or prior commands to construct later work without the CPU issuing one call per object. Source: [OpenGL 4.6 draw reference pages](https://registry.khronos.org/OpenGL-Refpages/gl4/html/).

## shader compilation, linking, and use

OpenGL accepts GLSL source, compiles shader objects, links compatible stages into programs, validates interfaces, and selects a program or program pipeline for use. Compilation/link logs and interface queries expose the result to the application. Source: [Shader Compilation](https://wikis.khronos.org/opengl/Shader_Compilation).

## texture and image transfer

Commands allocate texture storage and move image data between host memory, pixel buffer objects, textures, and other images. Pixel-store state controls host-memory layout during transfers; texture formats and types define conversion into internal storage. Sources: [OpenGL Texture](https://wikis.khronos.org/opengl/Texture) and [OpenGL 4.6 reference pages](https://registry.khronos.org/OpenGL-Refpages/gl4/html/).

## framebuffer operations

Framebuffer operations attach/detach images, select draw/read buffers, check completeness, and define where rendering results go. Framebuffers are also the endpoints for blits, clears, resolves, and readback. Source: [Framebuffer Object](https://wikis.khronos.org/opengl/Framebuffer_Object).

## viewport and scissor

Viewport state maps post-projection coordinates into window coordinates; scissor state restricts raster/sample updates to rectangular regions. These are fixed-function controls applied outside the shader source. Source: [Rendering Pipeline Overview](https://wikis.khronos.org/opengl/Rendering_Pipeline_Overview).

## rasterization and culling

After primitive assembly, OpenGL clips/culls and rasterizes points, lines, or triangles into fragments/samples. Application state controls face culling, front-face orientation, polygon mode, line/point behavior, polygon offset, multisampling, and related raster rules. Source: [Rendering Pipeline Overview](https://wikis.khronos.org/opengl/Rendering_Pipeline_Overview).

## depth and stencil tests

Depth and stencil tests compare incoming fragment/sample values against framebuffer depth/stencil state and can reject or update samples according to configured functions and operations. They occur in per-sample processing around fragment-shader output. Source: [Rendering Pipeline Overview](https://wikis.khronos.org/opengl/Rendering_Pipeline_Overview).

## blending, logical operations, and write masks

Color blending combines source fragment output with destination framebuffer values; logical operations provide bitwise color combining for supported formats; write masks suppress selected color/depth/stencil components. These are fixed-function post-fragment controls. Source: [Rendering Pipeline Overview](https://wikis.khronos.org/opengl/Rendering_Pipeline_Overview).

## compute dispatch

`glDispatchCompute*` launches compute-shader workgroups without running the graphics/rasterization pipeline. Workgroup size comes from the compute shader and dispatch dimensions come from the API call or indirect buffer. Sources: [OpenGL Shader](https://wikis.khronos.org/opengl/Shader) and [glDispatchCompute](https://registry.khronos.org/OpenGL-Refpages/gl4/html/glDispatchCompute.xhtml).

## shader storage and image binding

OpenGL binds buffers to uniform/shader-storage/atomic-counter interfaces and binds textures as image units for shader load/store. These bindings expose general read/write resources to shaders beyond ordinary sampled textures. Sources: [Buffer Object](https://wikis.khronos.org/opengl/Buffer_Object) and [Image Load Store](https://wikis.khronos.org/opengl/Image_Load_Store).

## memory barriers

Because shaders and transfers can read/write shared resources asynchronously, OpenGL exposes memory-barrier commands that make selected classes of prior writes visible to later operations. The application identifies the kinds of subsequent accesses that require ordering/visibility. Source: [OpenGL Memory Model](https://wikis.khronos.org/opengl/Memory_Model).

## transform feedback

The transform-feedback operation begins/ends capture and writes selected outputs of the final vertex-processing stage into bound buffers. Rasterization may be disabled during capture, making this a way to use graphics stages as a stream-processing system. Source: [Transform Feedback](https://wikis.khronos.org/opengl/Transform_Feedback).

## queries and conditional rendering

Queries measure properties of submitted work; conditional rendering can make later drawing depend on an occlusion-query result without round-tripping that decision through the CPU. This is one of OpenGL’s limited mechanisms for device-side control of subsequent work. Source: [Query Object](https://wikis.khronos.org/opengl/Query_Object).

## synchronization

Fence syncs plus client/server wait operations allow explicit ordering with CPU access or later GPU work. OpenGL also has substantial implicit synchronization and ordering rules, which is why synchronization is less visibly pervasive than in Vulkan. Source: [Sync Object](https://wikis.khronos.org/opengl/Sync_Object).

## readback

Readback transfers rendered pixels, buffer contents, query results, and other state/data back toward host-visible memory. Because it can force synchronization, high-performance code generally avoids synchronous readbacks in the critical path or uses asynchronous buffer/query mechanisms. Source: [OpenGL 4.6 reference pages](https://registry.khronos.org/OpenGL-Refpages/gl4/html/).

## clear, copy, blit, and invalidate

OpenGL provides direct operations to clear resources, copy buffer/image data, blit between framebuffers (including resolves), and invalidate contents that need not be preserved. These are data-movement/lifetime primitives independent of ordinary draw shading. Source: [OpenGL 4.6 reference pages](https://registry.khronos.org/OpenGL-Refpages/gl4/html/).

## debug and introspection

The API exposes error/debug messages, object labels, implementation limits, object/program queries, shader/program logs, and interface introspection. These operations do not render directly but are primitives for discovering capabilities and observing the otherwise implicit state machine. Sources: [OpenGL Object](https://wikis.khronos.org/opengl/OpenGL_Object) and [OpenGL 4.6 reference pages](https://registry.khronos.org/OpenGL-Refpages/gl4/html/).
